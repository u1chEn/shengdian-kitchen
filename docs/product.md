# 剩点什么 · 产品说明

## 目标与场景

帮助只想利用现有食材快速决定一顿饭的人，减少从“有什么”到“怎么做”的选择成本。先聚焦日常家常菜，不承担库存管理、营养治疗、复杂过敏判断或任意食材生成。

## 核心流程

选择/输入现有食材 → 设置实际厨具、调料、人数和时间 → 比较可做菜品 → 打开绘本食谱 → 查看参考用量与步骤/复制做法。

## 关键取舍

| 问题 | 当前方案 | 原因 |
| --- | --- | --- |
| 不知道菜名，如何搜索 | 用冰箱和食材作为入口 | 用户能回答“有什么” |
| 勾选的东西必须全部放进一道菜吗 | 按菜谱匹配食材子集 | 不强行组合，避免浪费其他食材 |
| 为什么之前容易只看到汤 | 做法和厨具多样性排序 | 优先呈现可比较的不同做法 |
| 为什么暂不用实时模型 | 本地菜单，保留 API | 避免持续费用，便于复现与核对 |
| 图片如何帮助选择 | 每道菜对应成品插画 | 让用户比较成品，不拿原食材拼图冒充菜品 |
| 多人怎么做 | 用量换算，设备按容量分批 | 数量变化与烹饪时间分别处理 |
| 数据不够怎么办 | 明确显示限制与可调整条件 | 不编造不存在的材料或过敏保证 |

## 当前实现与真实证据

54 种食材、110 道菜谱、6 页冰箱、6 类厨具；推荐与约束由本地规则处理。测试覆盖菜谱可达性、用量和时长换算、约束与图片映射。暂未开展正式用户研究、留存测试或菜谱逐道试做，不写虚构的用户规模、效率提升和转化率。

## 面试演示（约一分钟）

“我从一个很小的生活问题出发：冰箱有剩余食材，但很难从这些东西反推出能做的菜。我把入口设计成一个可选择的冰箱，用户先告诉产品有什么，再看能做什么。推荐不要求用完全部食材，也会考虑厨具、调料和人数。为了控制演示成本并使结果能核对，默认采用内置菜谱和规则匹配，并增加需单独确认、仅发送做饭数据的DeepSeek接口。开发与插图使用了 AI 辅助，产品范围、流程、筛选约束和展示取舍可以在项目中逐项说明。”

以上是项目介绍范例，请按自己实际参与和理解的内容讲述，不夸大独立编程能力。

## 下一轮要验证

邀请少量目标用户，用他们真实的剩余食材完成找菜任务；观察首次找到可做菜的比例、从选择到打开食谱所需时间、空结果原因和步骤中仍需追问的内容。先记录真实基线，再确定改进目标。菜谱需安排实际试做和人工复核。
